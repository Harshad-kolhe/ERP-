Interface Design Specification · Phase 1

An ERP you operate, not one you navigate

The system this replaces had 180 list screens and no home. You signed in and were handed a menu. Everything after that was your own memory of where things live. This document proposes the shell, the navigation, and the dashboard that come instead — built on the design tokens already committed to the repository.

01

What the old system got wrong

Not a list of complaints — each of these is a measured finding from the audit, and each one dictates a specific design decision further down.

Was

Of roughly 180 list grids, 12 were genuinely server-paged. The rest fetched every matching row into the browser and paged it there.

Instead

One table component. Server paging is the only path through it, so the slow version is not something a developer can accidentally write.

Was

The menu lived in three database tables. Nobody could answer what screens existed without querying production.

Instead

Navigation is a typed file in source, filtered by permission. The feature surface is answerable by reading code.

Was

Ten modules each grew their own approval screen. A manager checked ten places to find what was waiting on them.

Instead

One inbox. Everything awaiting you, from every module, ranked by what it is holding up.

Was

Status was a bare literal. "01" appeared 277 times in the source; a single enum existed in the entire solution.

Instead

Named states, rendered as chips that carry a shape as well as a colour, so they survive colour-blindness and a bad monitor.

Was

No landing screen at all. The application opened on a login page and then a menu bar.

Instead

A home that answers one question — what needs me today — and links straight into the filtered list that resolves it.

02

Six principles

These are the rules the rest of the document follows. Each exists because of something the previous system did.

P1Numbers are doors, not decoration

Every count on the dashboard is a link into the exact filtered list that produced it. A figure you cannot act on is a figure nobody reads after week two.

P2Density is a feature

A purchase officer lives in this for eight hours. Rows are 30px, numerals are tabular, and the radius is tighter than the framework default. Airy dashboards are for software people demo them; dense ones are for people who use them.

Legacy carried 15-column grids. Fighting density loses.

P3State reads at a glance, without colour

Circle is healthy, triangle is warning, diamond is critical, square is inert. Colour reinforces the shape; it never carries the meaning alone.

P4The grid state lives in the URL

A filtered, sorted, paged view is a link you can paste into a message. The back button works. Nobody describes over the phone which filters to click.

P5Keyboard first for the entry roles

Stores and purchasing type all day. ⌘K goes anywhere, / focuses search, arrow keys move rows, Enter opens. The mouse stays optional.

P6Show the exception, not the total

"1,284 parts in stock" tells nobody anything. "7 parts below reorder, blocking 3 machines" is the same data doing work.

Why the business-unit switcher is in the chrome. In the old system the unit was a hidden session value applied by a LINQ helper each developer had to remember to call — and every query that forgot leaked another unit's data. It is now enforced by a database query filter that cannot be skipped. Putting the switcher permanently on screen makes the scope that is being enforced visible to the person it affects.

The command palette carries the long tail

Roughly 180 screens will never fit in a sidebar that stays readable. ⌘K searches screens and records in the same box — type M-2411 and the machine comes up; type grn and the goods-receipt screens do. The sidebar then only needs the twenty destinations people use daily, and the other hundred and sixty stay one keystroke away instead of four clicks deep.

What is deliberately absent. No revenue chart, no gauge dials, no "total parts" counter, no activity feed. None of them change what anybody does next. Every list has these parts: saved views, removable filter chips, column chooser, server-side export, server pager. Nothing bespoke.

The other three

Detail — a header of identity and state, tabs for lines, documents, history and approvals, and the action bar pinned bottom-right so it stays reachable on a long form. The audit trail is a tab, not a separate screen nobody opens.

Approval queue — the unified inbox. Each row shows what it is, who raised it, the value, how long it has waited and what it is holding up. Approve and reject are inline; opening the document is for when you need convincing, not a mandatory step.

Staged import — the Excel upload workflow, which was genuinely good in the old system and is worth keeping: upload, validate, preview with per-row errors, then commit or discard as one unit. Never a partial import that leaves half a BOM in the database.

07

What React is actually buying

You asked what justifies the rewrite on the interface side. Not "it is modern" — these are the specific things the old architecture could not do.

Navigation stops costing a page load

Every screen change previously meant a full round trip: a Razor view, then several megabytes of scripts that were served with no-store so they were re-downloaded every single time. Moving between two lists to compare them was a measurable wait. Client-side routing makes that instant, and the layout, sidebar and session state survive the transition.

One table component instead of a hundred and eighty

The old grids were written per screen, which is why 149 of them ended up client-paged: each was a fresh chance to get it wrong. A single component that only knows how to ask the server for one page makes the correct version the path of least resistance — and fixes all 180 screens when it improves.

Approve without losing your place

An approval marks the row done immediately and reconciles with the server underneath. Working through a queue of thirty stops being thirty page reloads. This is only safe because the API returns real status codes now — the old envelope returned HTTP 200 with Status: false inside, so the client could not tell success from failure and could not risk assuming.

A filtered view is a link

Grid state lives in the URL, so "the nine overdue POs" is something you paste into a message rather than describe over the phone. It also means the browser's back button behaves, which it never did before.

The shop floor can be treated differently

Job card and goods-receipt screens are used standing up, on a tablet, sometimes on bad wifi. Being a real client application means those screens can hold state through a dropout and submit when the connection returns. A server-rendered form simply loses the entry.
